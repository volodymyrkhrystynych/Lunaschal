# Learning (`backend/routes/learning.py`, `backend/learning/`, `src/components/Learning/`)

AI-augmented spaced repetition. All generated cards (brain-dump, journal, chat topic, verification follow-ups) land as `pending` in ONE approval queue (approve / steerable-regenerate / deny). `POST /generate` (BrainDump's route, `backend/ai/learning_generation.py`'s `generate_cards`) is the one call site that passes `backend/memory.py`'s standing document as optional reference material, so a misheard name in a dictated brain-dump gets fixed the same way Journal's Polish, Ideas' capture, and Food's structuring already do — `generate-from-journal`/`generate-from-note` don't, since their source text is already polished/typed by the time it reaches here. Scheduling is **FSRS** via the `fsrs` package (`backend/learning/scheduler.py`; `fsrs_state=NULL` = never reviewed/reset). A review session hands out `DECK_SIZE` (10) due cards and is **resumable**: every answered or flipped card is persisted to `learning_attempts` (one open row per card, deleted in the same transaction as its rating), so leaving the view or reloading never re-asks a card. `/due` sorts open-attempt cards first so a resumed deck always contains them; the client seeds its session from `/due` + `/attempts` and keeps local state authoritative from there. Grading is claim-coverage: cached claim decomposition → coverage check → pre-selected Again/Hard/Good/Easy the user can override. It runs **after** the answer is saved, as an `llm_jobs` row drained by `backend/ai/jobs.py`'s single worker (`backend/learning/attempts.py`) so it queues rather than blocking the submit — and unlike the in-memory queue it replaced, it survives a restart. Deliberately **P1** despite the answer being saved first: you are looking at the card waiting for its grade; the result lands on the attempt row and the client polls it in. Answer embeddings live as float32 blobs on `learning_cards` (in-Python cosine, `backend/learning/dedup.py`) powering the approve-time duplicate **hint** (never auto-reject) and the low-similarity grading gate; both silently disable without an embedding provider. Folders bind at most one MCP evidence provider (`mcp_servers` registry) for verification — trust-first: no provider/no hit ⇒ "no authoritative source found", never open-web. **A spoken answer is uploaded as its attempt** (`POST /attempts/recording`, client-minted id, replay a no-op checked before the file is read): the phone is on the next card the moment recording stops, so the clip waits at `<LEARNING_ROOT>/<attempt_id>/answer.<ext>` (`backend/learning/storage.py`) and `grade_attempt` transcribes it first — the words are committed to `answer` and the clip deleted *before* grading, so an interrupted grade re-runs on text; a failed transcription keeps the clip until the card is rated. **Cards are never retired by reviewing** — FSRS just keeps lengthening the interval, and "mastered" (stability ≥ 21 days) is only a stats bucket. `POST /cards/<id>/retire` is the explicit way out: `state='retired'`, history kept, open attempt closed. Revising an active answer also retires the card (`revised_from` links versions, append-only `learning_revisions` log) and resets FSRS only for semantic changes. Deletes are hard deletes; FKs null `derived_from`/`revised_from` breadcrumbs.

**Review cards** (`backend/learning/review_cards.py`, `learning_cards.kind='review'`) are the one kind that skips the queue: an iPad notebook saved with its **For review** switch on sends `forReview` with `POST /api/journal`, and the entry becomes an `active` card in the app-owned **For review** folder (`learning_folders.system_key='review'`, created at startup, 409 on rename or delete), first due at the next 4am. A review card has **no back side** — `answer` is empty and the front is the entry's image attachments, read live by `review_payloads` on `/due` and `/cards` so pages that upload after the create and a title written later both appear. It is rated straight from the pages with `answerMode:'self'` and never becomes an attempt, so attempts, revise, chat and verify all 400 on it. One per entry (partial unique index on `source_id`); a trigger deletes it with its entry, and a newspaper re-filed with `replaces` carries the card — schedule and all — to the new entry instead.
