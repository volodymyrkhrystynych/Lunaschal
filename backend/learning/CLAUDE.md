# Learning (`backend/routes/learning.py`, `backend/learning/`, `src/components/Learning/`)

AI-augmented spaced repetition. All generated cards (brain-dump, journal, chat topic, verification follow-ups) land as `pending` in ONE approval queue (approve / steerable-regenerate / deny). `POST /generate` (BrainDump's route, `backend/ai/learning_generation.py`'s `generate_cards`) is the one call site that passes `backend/memory.py`'s standing document as optional reference material, so a misheard name in a dictated brain-dump gets fixed the same way Journal's Polish, Ideas' capture, and Food's structuring already do — `generate-from-journal`/`generate-from-note` don't, since their source text is already polished/typed by the time it reaches here. Scheduling is **FSRS** via the `fsrs` package (`backend/learning/scheduler.py`; `fsrs_state=NULL` = never reviewed/reset). A review session hands out `DECK_SIZE` (10) due cards and is **resumable**: every answered or flipped card is persisted to `learning_attempts` (one open row per card, deleted in the same transaction as its rating), so leaving the view or reloading never re-asks a card. `/due` sorts open-attempt cards first so a resumed deck always contains them; the client seeds its session from `/due` + `/attempts` and keeps local state authoritative from there. Grading is claim-coverage: cached claim decomposition → coverage check → pre-selected Again/Hard/Good/Easy the user can override. It runs **after** the answer is saved, as an `llm_jobs` row drained by `backend/ai/jobs.py`'s single worker (`backend/learning/attempts.py`) so it queues rather than blocking the submit — and unlike the in-memory queue it replaced, it survives a restart. Deliberately **P1** despite the answer being saved first: you are looking at the card waiting for its grade; the result lands on the attempt row and the client polls it in. Answer embeddings live as float32 blobs on `learning_cards` (in-Python cosine, `backend/learning/dedup.py`) powering the approve-time duplicate **hint** (never auto-reject) and the low-similarity grading gate; both silently disable without an embedding provider. Folders bind at most one MCP evidence provider (`mcp_servers` registry) for verification — trust-first: no provider/no hit ⇒ "no authoritative source found", never open-web. Revising an active answer retires the card (`revised_from` links versions, append-only `learning_revisions` log) and resets FSRS only for semantic changes. Deletes are hard deletes; FKs null `derived_from`/`revised_from` breadcrumbs.

**Review cards** (`backend/learning/review_cards.py`, `learning_cards.kind='review'`) are the one kind that skips the queue: an iPad notebook saved with its **For review** switch on sends `forReview` with `POST /api/journal`, and the entry becomes an `active` card in the app-owned **For review** folder (`learning_folders.system_key='review'`, created at startup, 409 on rename or delete), first due at the next 4am. A review card has **no back side** — `answer` is empty and the front is the entry's image attachments, read live by `review_payloads` on `/due` and `/cards` so pages that upload after the create and a title written later both appear. It is rated straight from the pages with `answerMode:'self'` and never becomes an attempt, so attempts, revise, chat and verify all 400 on it. One per entry (partial unique index on `source_id`); a trigger deletes it with its entry, and a newspaper re-filed with `replaces` carries the card — schedule and all — to the new entry instead.

**Agent lessons** (`backend/learning/lessons.py`, `backend/ai/learning_lessons.py`, `learning_lessons`, the **Import** mode) turn a coding agent's daily learnings files into cards. The agent half is only a convention — the snippet in `src/lib/agentLearnings.ts`, mirrored in [docs/agent-learnings.md](../../docs/agent-learnings.md) and kept equal by a test — so nothing here talks to an agent: files are uploaded/pasted, or read from an inbox folder (`settings.learnings_inbox_path`) that is rescanned by a `POST /lessons/scan` the Learning tab fires on mount (never a side effect of a GET). `parse_lessons` splits on `## `, and **dedup is on each lesson's own text, not the file** (`content_hash` UNIQUE), because a day's file is appended to all day and must re-import as only its new sections; the user's files are read and never moved. Each new lesson is a `learning.process_lesson` job (P2): the nearest `MAX_CANDIDATES` cards by embedding — **live or still pending**, so two copies of a lesson in one batch find each other — go to a grammar-constrained judge that names the covering card or none; a covered lesson keeps the card and the one-line reason and makes nothing, and `POST /lessons/<id>/force` overrides it without asking the judge again. Otherwise it becomes scenario cards (`source_type='agent_lesson'`, `#lesson`, the folder from `settings.learnings_folder_id`) in the normal approval queue — scenarios that never name the principle, since recognising _when_ it applies is the skill. A paused or preempted model leaves the lesson `pending` rather than `error`.

**Retiring from review**: `POST /cards/<id>/retire` sets `state='retired'` (keeping FSRS state) and deletes the card's open attempt, from a Retire button on both rating slides. The client waits for it before advancing, unlike a rating, because finishing a session refetches `/due` and an in-flight retire would hand the card straight back. `retired` has two meanings that share the state — taken out by the user, or an old version a revision replaced — and `/cards?state=retired` marks the second `superseded`; only the first can be unretired (409 otherwise), from Browse's "Show retired cards".
