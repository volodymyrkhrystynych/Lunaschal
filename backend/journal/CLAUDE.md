# Journal attachments (`journal_attachments`, `backend/journal/storage.py`, `src/components/JournalAttachments.tsx`)

Audio, video and photos hung off a journal entry, added/renamed/deleted in the entry's edit mode and playable/readable outside it. Files live under `./data/journal/<attachment_id>/` (`JOURNAL_ROOT`), never as blobs, and uploads **stream to disk** (`file.save`, not `read()`) because a phone video is happily several hundred MB. Things to know:

- **Every attachment is held on the device until the server confirms it** — the same promise the recordings below already made, and the reason this section is no longer only about audio. A file picked, pasted, dropped or staged in the composer is written to `photoStore` (`target: 'journal'`) _before_ anything is POSTed, then uploaded by a registered offline mutation that retries, pauses while the backend is unreachable, survives a reload, and is swept up at boot by `resumeStoredPhotos` if the tab died before the mutation reached the persisted cache. `POST /api/journal/<id>/attachments` therefore takes an optional client-supplied `attachmentId` and returns the row it already holds rather than storing a second copy — the same replay contract `/api/journal/recordings` has, and the early return happens before the file is read. The create and its attachments share `JOURNAL_LANE` (a react-query mutation scope) so a queue replayed after a reload cannot send a photo at an entry that has not landed yet. Until this existed the composer uploaded staged files with a bare `fetch`, no retry, holding them nowhere but React state: on a phone with spotty wifi the picture was gone the moment the request failed, while the recording staged beside it came back — because `recordingStore` had been holding it all along.
- **Paste and drop are first-class, not a convenience.** The capture happens on the whole editor (`JournalAttachments` wraps the title/body fields as its own paste target) because the media is recorded on a phone or iPad, where exporting to Files and picking it back out is the step being deleted. A paste carrying no media falls through to the textarea untouched. The compose box for a _new_ entry stages files in local state until Save, because the entry has no server-side row for them to hang off yet; `submitNewEntry` then mints its id, writes each staged file to the device and queues it behind the create (above). **Both work on the desktop and neither works on iOS** — getting a Voice Memos recording in is unsolved, and [docs/learnings/ios-voice-memo-capture.md](../../docs/learnings/ios-voice-memo-capture.md) records the dead ends (and why iOS Shortcuts is the next thing to try) so they aren't re-walked. An upload with an empty filename is legitimate and must stay supported either way.
- **A recording is held the same way, in its own store.** `recordingStore` stays separate from `photoStore` because audio is captured _over time_ — chunk-by-chunk appends, a finalized flag, a recovery path for a recorder the OS killed mid-sentence — while a file is complete the instant it is picked. A composer clip also carries `entryId` on the stored recording, not just in its upload's variables: the boot sweep finds an orphan by enumerating the store, and one that has forgotten its entry is filed as a bare journal entry of its own beside the words it was recorded with.
- **A recording made in the app is held on the device until the server confirms it.** `POST /api/journal/recordings` takes the entry id _and_ the attachment id from the client, because the phone re-POSTs the same clip on every reconnect until it lands — so a replay must be a no-op (`INSERT OR IGNORE` for the entry, early return on an attachment id we already hold, checked before the file is read). The browser side writes audio to IndexedDB every five seconds while recording, since iOS suspends a backgrounded page and a screen lock used to destroy the whole take. Design record: [docs/learnings/durable-journal-recordings.md](../../docs/learnings/durable-journal-recordings.md).
- **The same route is how the Ideas tab records.** An extra `ideaId` makes one upload create three things — the entry, its attachment and the idea — and `_transcribe_attachment_bg` writes its one transcription into both the entry body and the idea (`_deliver_idea_transcript`). The entry is an ordinary journal entry afterwards: it keeps the recording when the idea is deleted, and `journal_entries.idea_id` is `ON DELETE SET NULL` so the link goes and nothing else does. See [backend/research/CLAUDE.md](../research/CLAUDE.md).
- **And how the reader's commentary microphone records.** An extra `ficId` (plus a `chapterId`, absent for a PDF fic) makes the same upload write a `journal_entry_fic_refs` row, so the entry is commentary _on a chapter_ from the moment it exists — `_link_recording_fic`. It rides along with the audio rather than following as a `POST /api/fanfic/<id>/journal-link` call for the same reason `ideaId` does: this upload is replayed until it lands, and a separate request is the one step that can be lost. What it would lose is the only thing saying which chapter the entry was about. An unknown fic (or a chapter from a different one) drops the link and keeps the recording — the audio is the irreplaceable half.
- **`kind` is `audio | video | image`, and mime beats extension** (`storage.resolve_upload`): mp4/webm carry either, so only the upload's mime type separates a voice memo from a clip. With no usable mime an ambiguous extension defaults to video — audio in a `<video>` costs a blank frame, the reverse throws the picture away.
- **Video takes the speech path, not the vision one.** ffmpeg pulls the audio track out of the container, so `_do_attachment_audio` handles it unchanged.
- The user-given `name` is the point (an attachment is "what this is about", not a filename), and **transcription/captioning is opt-in per attachment, never on upload** — it costs a real CPU transcription here, and a voice memo is often kept as audio. Both run on `run_bg` and report through `transcript_status`, with results pushed over the existing `/api/journal/events` SSE stream.
- Photo captioning and audio description both need the **Multimodal input** checkbox (Settings → llama.cpp), which writes the one `gemma4-12b-omni` alias into both `llama_vision_model` and `llama_audio_model`. The chat preset sets `mmproj-auto = false` and takes text only, so both go to that separate CPU-only any-to-any model — a ~7.4 GB download, which is why it ships **off** and says so. It stayed off longer than intended: the checkbox used to write `gemma4-vision`, a preset that was never defined, so captioning had never once worked — see `backend/ai/images.py`.
