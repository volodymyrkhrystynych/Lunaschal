# Ideas (`backend/routes/ideas.py`, `backend/research/`, `backend/repos/`, `src/components/Ideas/`)

A feature backlog for **any number of registered repositories**, developed with an agent that reads their code. Master-detail: list + capture box on the left, idea detail on the right. Design record and the decisions the build settled — including what is deliberately _not_ built: [docs/ideas-tab.md](../../docs/ideas-tab.md). Things to know:

- **A repo is registered by git URL and cloned into `./data/repos/<slug>/`** (`REPOS_ROOT`), so Luna owns every checkout and can `reset --hard` without destroying anyone's work. `backend/repos/` holds it: `storage.py` (the layout, and the one `resolve_within` every code tool goes through), `git.py`, `graph.py`, `registry.py`, `job.py`. `ops/backup.sh` excludes `repos/` — a checkout plus its graph and cache is tens of MB per repo for bytes one `git clone` away.
- **`assert_clone_url` is not `web.py`'s SSRF guard**, and confusing them gets both wrong. There, the _model_ picks URLs. Here the user types one, so the threat is what git does with it: `ext::` runs an arbitrary command by design, `file://` clones off this machine, and a leading `-` is read as a flag (`--upload-pack=<cmd>` is RCE on this side). https and the two SSH spellings only; pure, and unit-tested by its refusals.
- **Pull is `fetch` + `reset --hard`, never `git pull`.** The clone carries an untracked `graphify-out/`, and a merge-based pull is one conflict away from wedging a checkout nobody is watching. Reset leaves untracked files alone, and nothing ever writes into a clone, so there is no local work to lose.
- **`graphify update <path>` builds a graph from nothing** — there is no separate build command, extraction is AST-only with no LLM and no API key, so one call covers both the import and every nightly pull. `--force`, because the tree was just reset to the remote and a commit that deletes a package _should_ shrink the graph. A failed build costs the `code_map` tool, never the checkout.

- **An idea keeps `raw_content` and `content` separately**, the same contract as `journal_entries`: `raw_content` is what was dictated or typed and is never overwritten; `content` is the AI-cleaned prose. The detail pane shows `content` when it exists and falls back to `raw_content`, with the transcript still reachable under "As captured". `POST /api/ideas/voice` fills in `content` with a background pass (`backend/ai/idea_polish.py`'s `polish_idea`, `_enrich_idea_bg` in `backend/routes/ideas.py`) — light cleanup plus fixing a word `backend/memory.py`'s standing document gives a specific reason to fix, same reference Journal's Polish reads. It never raises and has no manual retry: a failed or no-op pass just leaves `content` empty for the existing fallback to cover, since nothing is waiting synchronously on it.
- **`_enrich_idea_bg` then names the idea** (`backend/ai/idea_title.py`), in the same job and after the polish, because the name should come from the corrected text rather than the transcript the polish just fixed. Typed capture is named but **not** polished — `content` is the AI's cleanup of a _transcript_, and rewriting what someone typed by hand is a different contract. The write is guarded (`AND (title IS NULL OR title='')`), so a name typed into the detail pane during the tens of seconds this takes always wins; `display_title` / `displayTitle` remain the fallback for the window before it lands and for an unconfigured model. The pane re-asks for an untitled idea every 4 s for its first three minutes and then stops — with no AI configured the title never arrives, and a poll with no end is a request every few seconds forever. A dictated idea polls on the same interval but for half an hour, because its text is behind a speech-to-text pass as well; that window is bounded for the same reason, since a transcription wedged in a live process would otherwise be watched forever (one that died with the process is reset to idle at startup).
- **An open question always carries 2–4 options.** The schema requires them (`minItems: 2`, so llama-server's grammar produces them during decoding) and `assess.normalize_options` trims, dedupes and drops the model's own "Other" — the UI owns that row. A decision the model could only phrase as prose is a question, not a fork; a question that arrives with no usable options still reaches the user, degraded to the write-in row alone.
- **Recording an idea saves it when you stop, and files it as a journal entry too.** The capture box's Record button follows the Journal button's contract, not `BrainDump`'s: the clip is written to IndexedDB while it is being recorded and uploaded through `POST /api/journal/recordings` carrying an `ideaId`, so one request creates the journal entry, its audio attachment and the idea, and `_transcribe_attachment_bg` writes one transcription into both halves (`_deliver_idea_transcript` → `apply_recording_transcript`, then the usual `_enrich_idea_bg`). It used to append the transcript to the textarea and wait for Save — fine at a desk, wrong on a phone, where the recording only ever existed in memory and anything that interrupted it lost the idea outright. Typing still works exactly as before; the textarea and Save are untouched.
  - The link is `journal_entries.idea_id` (`ON DELETE SET NULL`): deleting the idea keeps the entry **and the recording**, and the journal's pill disappears because the id goes with it. Deleting the entry leaves the idea with the text it already has, and `recording` on the detail fetch simply resolves to null. A transcript that lands after either deletion is dropped — both sides are guarded, and `apply_recording_transcript` also refuses to overwrite text typed into the idea while it was still transcribing.
  - The idea id is minted before the first chunk and stored **beside the audio** (`RecordingIdea` in `src/offline/recordingStore.ts`), not held in the component: the retry button and the startup sweep know only what is in that store, and a resumed upload that had forgotten its idea would quietly file the clip as a plain journal entry.
- **Dictation elsewhere in the tab still appends rather than saving** (`useRecorder`, the `Learning/BrainDump.tsx` pattern): a decision's write-in box is committed once and read by the planner afterwards. The discussion is the exception and matches the Chat tab instead — **dictation sends**, carrying anything already typed with it, because a chat turn is cheap to correct by sending another.
- **The detail pane is four tabs — Idea, Decisions, Discuss, Plan** (`src/components/Ideas/IdeaDetail.tsx`), not one long scroll. The discussion is a chat and a chat needs the whole pane: as a section at the bottom of the scroll its composer slid down the page as the answer streamed in. The Decisions tab carries the open count so it is visible from any tab; `IdeaAssessment` keeps the verdict and its evidence, and `IdeaDecisions` owns answering.
- **The editor tracks a baseline, not the query cache.** `src/lib/ideaSave.ts` holds the whole state machine (`saved` / `dirty` / `saving` / `error`) and the merge, both pure. Comparing the draft against the cache is what produced a permanent "Saving…" with no request in flight: on the render where the fetch lands, the hydration effect has set state but the autosave effect still closes over the empty fields, so it declared a difference and then returned early — before clearing the flag — on the render that matched. Against a baseline, `dirty` is a fact about what was typed, `saving` means a request is genuinely in flight, and the background naming pass can move the server's copy without ever looking like unsaved work. Untouched fields adopt what the server now says; edited ones don't, and their baseline advances anyway so the _other_ field's background write cannot resurrect as a phantom local change. A pending save is flushed on blur, on Ctrl/Cmd+S, on clicking the indicator, and on unmount — switching ideas used to drop whatever was inside the debounce window.
- **A sketch is a Paper _page_, not a whole paper** (`idea_sketches` → `paper_pages`), rendered straight from the page's PNG snapshot at `/api/paper/pages/<id>/image` — no copying and no new storage, the same borrowing `JournalPaperItem` does. Deleting the page cascades the sketch.
- **The caption on a sketch is the feature, not decoration.** The research agent runs on the chat model, which is text-only (`mmproj-auto = false`), so it reads the caption and the image is for the human. The `[gemma4-12b-omni]` preset added for journal attachments does not change this — it is not wired into the agent, and would not be worth a CPU-only vision call mid-loop. The UI says so out loud — a "describe this sketch" button that always errored is the journal-photo-captioning mistake.
- `page_image_url` in `backend/routes/paper.py` is exported (not `_`-prefixed) precisely because Ideas borrows it; keep it that way.

**The code toolbox** (`backend/research/code.py`) is what makes the tab do its job. Before it, the agent's only picture of the codebase was `repo_facts.py`'s inventory, and `discuss.py`'s prompt said outright: _"Do not use them to look up things about Lunaschal itself; the inventory below is authoritative."_ That answers "is there a `paper_pages` table?" and cannot answer "is this loop racy?" or "where would this go?".

- **`code_search` (ripgrep), `read_file`, `list_dir`, `code_map` (graphify).** `CodeTools` is an object with a `run_tool`, which is the duck type `agent._loop` already dispatches to — **the shared loop is not modified**. Budgets change at the call site: `max_turns=24`, since the web-tuned 12 ran out while the agent was still orienting.
- **`code_map` is absent, not failing, when a repo has no graph** — the same degrade-by-absence `web.is_search_configured` uses. Its result carries a read-a-file-before-concluding reminder in the position `web.READ_ONE_REMINDER` was measured to work: on the freshest message.
- **Refusals are two layers.** `storage.resolve_within` refuses `.env`, `.git`, keys and anything resolving outside the clone (symlinks included — a clone is someone else's code and may contain any symlink it likes). rg _additionally_ gets glob exclusions, because it walks the tree itself and would otherwise print a line out of a `.env` before anyone asked to read that file.
- The **read budget lives in `CodeTools`**, not the loop, so the loop keeps one counter; a refused read costs nothing, or a model probing paths could burn the budget on files it never opened.
- `code.files_read(steps)` is the provenance helper: what was opened, never what the model says it read.

**The repo-context agent** (`backend/research/repo_facts.py`, `repo_scan.py`, `repo_job.py`, `repo_scheduler.py`) maintains a `repo_snapshots` row per repo describing what it currently is, so "you already built this" is evidence rather than a guess.

- **`repo_scan.py` is the half that works on any checkout** — module index, language mix, layout, doc headings — and `repo_facts.py` keeps the Flask/React/SQLite extractors, which return [] when their directories are absent, so a Rust crate needs no detection step. The module index is also the work list the nightly code-wiki pass rotates through.
- **A registered clone has no live database**, so its tables come from parsing `schema.sql` — columns added by `_ensure_*` ALTERs do not appear, and the digest says so out loud, because a missing column is otherwise indistinguishable from one that does not exist. Acceptable only because the agent can now read `connection.py` itself. This app's own scan still uses the exact `PRAGMA` path.
- **It is mostly not an LLM.** Routes come from an `ast` walk of the `@bp.<method>` decorators (which resolves each back to its Blueprint for the `url_prefix`), tables from `PRAGMA table_info` on the **live** DB (so `_ensure_*` migrations are included, which a parse of `schema.sql` would miss), views from the three hand-synced frontend literals. Pushing the repo through a 25 tok/s model nightly would cost tens of thousands of tokens to produce a lossy paraphrase of things we can read exactly. The model's only job is summarizing the `git log` delta — and it is nullable, because a failed summary must never cost the facts.
- **`view_facts` cross-checks `VIEWS` / `navItems` / `VIEW_ORDER`** and emits a warning when they drift. Those three are maintained by hand in three files, and a view missing from `VIEW_ORDER` simply can't be reached by the keyboard.
- **`CLAUDE.md`, `docs/architecture.md`, `docs/ROADMAP.md` and `docs/TODO.md` are read, never regenerated.** ROADMAP/TODO bullets are kept verbatim — they are the "planned but not built" ledger.
- Snapshot queries order by **`generated_at DESC, id DESC`**: `generated_at` is second-resolution, so the ULID is what actually orders two scans in the same second.
- Window defaults to 03:00–05:00, between the chat-title sweep (02:00–03:00) and the briefing (05:00–07:00), so the three never contend for the two llama slots.

**The research agent** (`backend/research/web.py`, `wiki.py`, `agent.py`, `backend/ai/priority.py`):

- **`backend/ai/priority.py` is a throughput gate, not a mutex.** llama-server has two slots, so a background loop and a chat message genuinely run at once — but they share memory-bound expert tensors, so the loop parks _between_ steps while a human waits. Nothing preempts a generation already in flight, which is why `chat_with_tools` now takes `max_tokens` and the research loop passes a small ceiling: **turn length is the granularity at which background work can yield.** The mark is acquired in the _view_ and released in the SSE generator's `finally` — acquiring inside the generator would leave time-to-first-token looking idle, and releasing outside it would leak on client disconnect. `MARK_TTL` and a `wait_for_idle` timeout mean a leak costs deferral, never starvation.
- **`run_bg` marks its work interactive** in one place, because journal polish and friends were triggered by a user action seconds earlier. Long agent runs deliberately do _not_ go on that executor — they would head-of-line block seven user-visible flows.
- **`web.py` is the only arbitrary outbound fetch in the app, and the model picks the URLs.** `assert_public_url` rejects non-http(s), `.local`/`.internal`, and any host resolving to a private/loopback/link-local/reserved address — re-run on every redirect hop, with manual redirect following. Search is pluggable (Brave key, or keyless self-hosted SearXNG); with none configured the tools return an explanatory _result_ rather than raising, so the loop degrades instead of dying.
- **Search requests are serialized, staggered, and circuit-broken**, not just guarded: `_dispatch` holds one process-wide lock for the whole call (concurrent callers — the Ideas agent and chat delegate deep-research both go through here — queue up rather than racing SearXNG or an API quota), enforces a minimum gap between requests, retries 429/503 and SearXNG-reported soft-bans (`unresponsive_engines` matching a CAPTCHA/rate-limit marker → `SearchSoftBlocked`) with the same fixed-backoff shape as `backend/fanfic/download.py`, and after `SEARCH_BREAKER_THRESHOLD` consecutive exhausted failures trips a cooldown that short-circuits further calls with `SearchCircuitOpen` — no network call, and `run_tool` tells the model outright not to retry. This is what stops a stuck agent from calling `web_search` a dozen times in a burst for zero results each time. A soft-ban SearXNG reports as **`Suspended:`** is the exception that isn't retried at all — while an engine is suspended (an hour after Brave's 429, a day after Startpage's CAPTCHA) SearXNG makes no request to it, so the backoff bought 50s of the identical empty payload; `SearchSoftBlocked.retryable` is False when every failed engine is suspended and that opens the breaker on the spot.
- **Which engines SearXNG asks is configuration, and it is load-bearing** (`searxng/settings.yml`). The four it enables for `general` by default — google, duckduckgo, brave, startpage — are exactly the four that block this box, and Google's block is silent (a JS interstitial that parses as zero results, so it never reaches `unresponsive_engines`). bing/yahoo/yandex/seznam answer; the measurements, the per-engine table and the one-command way to re-check are in [docs/learnings/searxng-engine-blocking.md](../../docs/learnings/searxng-engine-blocking.md).
- **The wiki is copy-on-write** (`wiki_revisions`, the `learning_revisions` pattern) — a background process editing prose the user relies on has to be auditable and undoable. A `locked` article rejects agent writes. Retrieval hands the model the whole index (`wiki_list`) rather than only a retriever: at a few dozen articles that costs ~1,200 tokens and beats any ranking function. **No embeddings** — the `embed` alias has `ctx-size 2048` so articles would need chunking, and its vectors are frozen because `learning_cards` depends on them.
- **Articles are scoped `UNIQUE(repo_id, slug)`, not globally** (`backend/db/wiki_repo_migration.py`). Two codebases will both have something worth calling `scheduling`, and one silently overwriting the other is not a conflict anyone would notice. `repo_id IS NULL, kind='research'` is a web note about a problem space — the only kind that existed before, and what every pre-existing row migrated to. A repo's agent sees its own articles **plus** the unscoped research ones, and never another repo's notes about a same-named module.
- **`kind` is a second scope, and it defaults to the work wikis.** `kind='life'` articles (`backend/lifewiki/`) also live at `repo_id IS NULL`, so an unfiltered unscoped `WikiTools` would hand this agent the user's sleep and eating habits while it researched a scheduling problem. `WikiTools(kind=WORK_KINDS)` is the default and covers `research` + `code`; the chat delegate takes the mirror image, `WikiTools(kind=LIFE_KIND)`, and never sees a code note. Widening the CHECK to allow `'life'` was a second create-copy-drop-rename in `wiki_repo_migration.py`, with the same two ordering traps as the first.
- **That migration has two ordering traps, both real.** `wiki_revisions` cascades on delete, so with foreign keys enforced `DROP TABLE wiki_articles` deleted the whole audit trail — enforcement is turned off before `BEGIN` (the pragma is a no-op inside a transaction) and restored in a `finally`. And `wiki_fts` is external-content keyed on rowid, whose triggers `DROP TABLE` takes with it, so the rebuild must run **before** `_init_wiki_fts`. Its index cannot live in `schema.sql` either: that file runs before every migration, and on an unmigrated table an index naming `repo_id` fails outright.

**The nightly pass** (`backend/research/code_wiki.py`, `backend/ai/code_wiki.py`, `repo_scheduler.py`) does, per repo: **pull, graph, scan, write.** The order is the point — a snapshot of a tree that was not pulled describes yesterday, and a note written against it cites lines that moved; a failed pull stops that repo rather than scanning a stale tree.

- **`plan_modules` is the whole policy**, reading only the DB and the snapshot's module index — the `research_job.plan_next` shape, testable without threads. Changed modules first (oldest note first among them: a note that no longer describes the code is worse than a missing one, because it will be retrieved and believed), then modules with no note, largest first, capped at `code_wiki_articles` per night. A full churn on a 25 tok/s model is hours of GPU time mostly rewriting articles that did not change.
- **The slug comes from the module path, not the model's title**, so a refresh lands on the same article. A retitled note is fine; a second article about the same directory is not.
- **Writing nothing is a real outcome** — `write_article` returns None when the model says it did not see enough, asked as a boolean because a boolean cannot be hedged. An invented note is worse than no note: it gets retrieved later and believed.
- **Tool turns are never streamed.** llama-server reconstructs OpenAI `tool_calls` from the model's native notation via a grammar it picks by reading that model's chat template (so `jinja = true` is what makes tool calling model-agnostic); reassembling partial tool-call deltas across chunks is how an argument goes missing in production. Gathering and answering are separate turns so the answer can stream while gathering stays blocking. `agent.gather_events` is a generator yielding `('step', …)` then one `('result', …)`, and `agent.gather` is the blocking wrapper — the SSE route needs the generator, because with the blocking form every tool event only arrives _after_ gathering ends, which is the silent spinner the events exist to replace.

- **`deadline` is checked where `checkpoint` is, and is deliberately not part of it.** A checkpoint raises; running out of time does not, because it is not a failure — the loop breaks, reports `timed_out`, and the caller decides. Both callers decide the same way (see `backend/delegate/CLAUDE.md`: salvage an answer from the transcript). Every bound the loop had before was a count — `MAX_TOOL_TURNS`, `MAX_FETCHES`, `TURN_MAX_TOKENS` — so a run that took an hour was inside all of them. A tool call skipped for lack of time still gets a tool message: the transcript is what the salvage turn is handed, and an assistant turn whose `tool_calls` have no replies is a malformed exchange. `agent.deadline_from(seconds, outer)` is the one place an inner budget is clamped to an outer one, and a disabled inner budget returns `outer` rather than None so it cannot silently remove the deadline wrapping it.
- **The research loop is the one daemon with no hour window** (`backend/research/research_scheduler.py`). The repo scan, briefing and title sweep are scheduled at night so they don't compete with the user; this one defers moment to moment through `priority` instead, which is what "runs whenever it likes but yields to anything you ask for" actually needs — and research is worth doing while the user is awake and about to read the answer. Each tick asks four questions (enabled? worker free? user quiet for `QUIET_SECONDS`? anything due?) and submits at most one task. `research_job.plan_next` holds the whole policy: assessment always before research (cheap, no web, and its output is what tells the research pass what to look for), nothing without a repo snapshot, nothing without a search provider, and a 24 h per-idea cooldown so a settled backlog doesn't re-research its newest idea every tick. **`research_enabled` defaults off** — the loop makes outbound requests.

**Assessment — "already built?" is evidence, not a vibe** (`backend/research/evidence.py`, `assess.py`, `backend/ai/idea_assessment.py`):

- **The model never writes a file path.** `gather_candidates` builds a numbered list of things in the repo the idea might already be satisfied by, each with a real `{kind, ref, file, line}`, and the JSON schema bounds `evidenceIndexes` to that list — so llama-server's grammar makes citing a nonexistent file impossible during decoding.
- **A deterministic clamp runs after the call**: no citations ⇒ verdict forced to `no` (confidence ≤ 0.4); `yes` with fewer than two citations ⇒ downgraded to `partial`. A confident uncited "yes" is the one output that could make the user drop an idea they should have built.
- **Being on the roadmap is tracked separately from being built** — they're opposites, and conflating them is how a backlog item gets marked done because someone wrote it down.
- Each assessment records the `snapshot_id` it judged against, so the UI marks it **stale** once the repo moves rather than presenting an old verdict as current. `ideas.user_verdict` always overrides the agent's.
- Open questions are upserted by a normalized `question_key`, so a re-run never resurrects one the user already answered.

**Discussion and plans**: `conversations.idea_id` is a second discriminator after `writing_project_id` — **six queries** filter "a general chat conversation" and all of them need `AND idea_id IS NULL` (`backend/routes/chat.py:20,30,51,81`, `briefing_job.py`, `chat_title_scheduler.py`). `backend/research/plan.py::render_plan_markdown` is pure, and the sections that must be exact — what already exists, which decisions are settled, which are still open — are stitched in from real rows rather than paraphrased by the model.

- **`discuss.build_toolbox` assembles the tools per discussion**, because they depend on which repo the idea is about and whether that repo has a graph; `discuss.system_prompt` is built from the same answer, since promising tools the model does not have is the same mistake as offering one that always fails. An idea with no repo falls back to the registered default, so a single-repo setup needs no configuring.
- **A plan's `filesToTouch` is bounded the way evidence is** (`backend/research/plan_files.py`): the server builds a numbered list of files somebody actually _opened_ — during this idea's discussions, then cited by the assessment, then read by the nightly pass — and the schema bounds `fileIndexes` to it, so the grammar makes an unreadable path impossible during decoding. No candidates ⇒ the field is dropped from the schema and unmentioned in the prompt, rather than offered as an always-empty array.
