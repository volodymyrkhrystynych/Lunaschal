# Study (`backend/study/`, `backend/routes/study.py`, `src/components/Study/`)

A reading desk: the thing you are learning from on the left half of the screen, the notes you are taking on the right. A **source** is a PDF, a web page archived as sanitized HTML, or a YouTube video pulled down with `yt-dlp`; the row stores only a path, the same layout fanfic/meetings/paper use — but there are **two roots**, see below.

- **Videos live on the archive drive and nowhere else; PDFs and pages live on the SSD.** `<STUDY_ROOT>/<source_id>/` (`./data/study/`) holds a PDF or an archived article — small, genuinely irreplaceable (an uploaded PDF has no source URL), and inside the tree `ops/backup.sh` mirrors. A downloaded video goes to `<settings.backup_path>/archive/study/<source_id>/` instead, beside the `archive/piano` already there, because a lecture is a few hundred megabytes that `yt-dlp` can produce again — mirroring it would mean the nightly job carrying three copies of a file nobody would ever restore. **`ops/backup.sh` needed no change for this**: the archive is a _sibling_ of the rsync destination and outside its source, so moving the bytes out of `data/` removed them from both the drive mirror and the tablet copy at once. `storage.ARCHIVED_KINDS` is the one place the split is decided; `source_file_path`/`source_dir` take the kind, and `resolve_stored_path` accepts a direct grandchild of _either_ root and still refuses everything else.
- **An absent archive root means unavailable, never "create it".** The target is a removable drive, and a mountpoint whose filesystem is not mounted is just an empty directory on the system SSD — a `mkdir -p` followed by a 279 MB download would pour it into the root partition and look exactly like success. So `import_youtube` checks the drive **before** the metadata pass and fails the row with the reason; it never falls back to `STUDY_ROOT`. `backend/email/media.py` states the same rule for the mail archive, and the resolution itself is shared: `backend/archive_location.py` (`resolve`/`require_root`) is what Piano's `archive.location()` and Study's `storage.archive_root()` both call, extracted rather than copied for the reason the SSRF fetch loop was.
- **A video on a disconnected drive is listed, not hidden.** Piano's model: the catalog stays browsable and the file 404s. `_attach_availability` puts `fileAvailable`/`fileUnavailableReason` on each row (resolved once per listing — it reads `settings` and stats the drive), `viewerKindFor` returns `'offline'` ahead of the kind, and the desk explains it. A `<video>` pointed at a 404 is a silent black box, which is the one thing this must not be. Consequently **Retry replaces the failed row rather than appearing beside it** — plug the drive in, hit Retry, and the recovery is complete; the old row is deleted only once the replacement import has actually started.
- **Study is the app's only _size_-gated view, and that is not the same gate as Piano's.** `desktopOnly` in `navItems` means "running inside the PyWebView window", which the GPD Pocket 2 satisfies — and a two-pane reading desk on a 7" screen is exactly what this must not offer. `largeOnly` is the new flag, driven by `LARGE_QUERY` (`min-width: 1024px`) in `src/lib/breakpoints.ts`. Both gates go through one pure `visibleNavItems` (`src/lib/navVisibility.ts`) so the sidebar's rendered list and the shortcut cycle's `availableViews` cannot disagree — they were two copies of the same filter expression, and this would have made three. `App.tsx` also falls back to `'chat'` when the persisted view is one this device cannot show: a phone whose last session ended on Study (or, before this, on Piano) came up to a blank `<main>`.
- **Notes are Notebook files, not a store of their own.** The right half mounts `NotebookEditorPane` on the path in `study_sources.note_path`, so vim bindings, `[[wiki links]]`, `:find`, checkbox toggling and the offline-aware debounced save are the ones already built, and a study note is reachable from the Notebook tab, its index and `:find` like any other note. The pane gained one prop for this: `homePath` (with `homeLabel`), so `:q` returns to the source's own note instead of navigating the reading pane off to `index.md`. A source gets its note lazily, the first time it is opened rather than at import — a source you only skimmed leaves no empty note behind.
- **The web import reuses `research/web.py`'s SSRF guard, and that meant factoring rather than copying.** `web_fetch` restricts itself to text types and hands back _stripped text_; the archive needs the HTML. `fetch_public_page(url, allowed_types=, max_bytes=)` is now the guarded fetch on its own — one redirect loop in the codebase, re-running `assert_public_url` on every hop — and `web_fetch` is that plus the strip. A second copy of that loop is precisely how the retired `websearch/agent.py` ended up without the guards the original had. Both limits default at _call_ time, not in the signature: binding them as default arguments froze them at import and silently disarmed `test_fetch_stops_reading_once_the_byte_cap_is_passed`, which monkeypatches the module global.
- **The archived page is sanitized _and_ sandboxed.** `nh3` runs before the file is ever written (a wider tag set than `fanfic/sanitize.py`'s — an article's headings, figures and tables are its content), and the file is still served into an `<iframe sandbox="">`. `allow-same-origin` is deliberately absent, which is what puts the frame in an opaque origin: the file is third-party markup on our own origin, so one layer of "this is safe" is not a layer. The title is read off the **raw** body, because nh3 drops `<head>` along with everything else outside the allowed set.
- **`yt-dlp` and `ffmpeg` are system binaries, not Python dependencies** — the same shape `backend/jobs/resume_review.py` uses for `pdftotext` (`shutil.which`, `subprocess.run` with a timeout, a clear error when absent) rather than pinning a package that needs updating every time YouTube changes. Two passes: `-J` for the title and duration, which is written to the row **before** the download so the library shows what is arriving rather than a bare URL for the next twenty minutes, then the download itself. The URL is normalized through `youtube.watch_url(parse_video_id(url))` first, so a `&list=` on the pasted link cannot turn a single-video import into a playlist download behind `--no-playlist`'s back. `parse_video_id` is pure and covers `watch?v=`, `youtu.be/`, `shorts/`, `embed/`, `live/`; anything else is refused rather than guessed at.
- **The format selector names H.264 + AAC, and that is not a quality preference.** Left to itself yt-dlp picks AV1 + Opus for anything modern on YouTube, and **Safari cannot decode AV1 without a hardware decoder** — Apple's first is the A17 Pro / M3, so every 12.9" iPad Pro (A12Z 2020, M1 2021, M2 2022) fails to play it, with no software fallback and no error worth the name: the player just sits there. That is the one device this large-screen-only tab exists for, so codec compatibility outranks compression efficiency. This was found by importing a real video, **not** by a test — every `yt-dlp` call in `test_study.py` is stubbed, so the suite was fully green while the feature was unusable on its target device; `test_youtube_download_asks_for_h264_within_the_height_cap` now pins the intent, but only the intent. `YTDLP_MAX_HEIGHT` is 720 for a separate reason: that iPad is 1366 CSS pt wide in landscape, so a half-width pane is ~683 pt — 1366 physical px at 2x — and 1280x720 is already pixel-matched, with 1080p oversampled for a split view. Measured on one 25-minute lecture: AV1 1080p 229 MB, H.264 1080p 572 MB, H.264 720p 279 MB.
- **`send_file(..., conditional=True)` on the file route is load-bearing for video** — it is what answers Range requests, and without it seeking a downloaded lecture silently does nothing. Note that `conditional=True` and `max_age=` are used mutually exclusively across this codebase.
- **A source's stored path never leaves the server.** `file_path` is absent from the route's column list, and the file route looks the path up in the DB and runs it through `storage.resolve_stored_path` (which only serves a direct grandchild of one of the two roots) before `send_file`.
- **An import that dies with the process leaves a row claiming to be running.** `import_status`/`import_error` mirror `fics.download_status`/`download_error`, and `_reset_stale_study_imports` in `connection.py` flips an orphaned `'importing'` to `'error'` at startup — `'error'` rather than `'idle'` because nothing re-arms an import on its own; the library's Retry is what starts it again. In-flight progress lives in the same in-memory registry pattern `fanfic/download.py` uses, cancellation modelled as absence from it, which is also what `DELETE` relies on to stop a running import from writing to a row that is about to disappear.
- **The PDF is rendered by pdf.js, not handed to the browser.** An `<embed>`/`<iframe>` PDF shows page one and nothing else inside a frame on iPad Safari — half the devices this tab exists for. Rendering it also gives a real page number, which is what a "resume where I left off" would hang on. The worker is resolved through `new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url)` so Vite bundles it locally and the desktop shell needs no network. Pages are rasterized at `devicePixelRatio` and scaled back in CSS; re-rendering on zoom is deliberate, because scaling a canvas with CSS is how a PDF goes blurry.

- **`study_sources.position` is one column with two meanings, and `kind` is what disambiguates it** — a page number for `pdf`, seconds for `youtube`. A `position_kind` column would only ever repeat what `kind` already says. **An article stores nothing, permanently**: the archived page renders inside `<iframe sandbox="">`, which is an opaque origin, so its scroll offset is neither readable nor settable from outside — and every way of reaching in weakens the second safety layer that frame exists to be, for a scroll offset. A `REAL`, not an integer, because `video.currentTime` is fractional.
- **Restoring a PDF page has to wait for the canvas that page is on.** `PdfViewer`'s render loop appends pages sequentially inside an async IIFE, so `canvas[data-page="214"]` does not exist at load time and scrolling to it on mount silently does nothing. A `pendingPageRef` consumed _inside_ the loop, as the matching canvas is appended, is the deterministic version — `src/components/Fanfic/Reader.tsx` solves the same problem for chapter text. Two consequences: while a restore is outstanding the scroll handler reports nothing (the pages under the viewport are whatever has rendered so far, and reporting them would overwrite the position we are travelling to), and a **zoom change re-arms it**, because the loop rebuilds every canvas and sends the scroller back to the top. Zooming is not moving. Video restores on `loadedmetadata` rather than mount, since `duration` is NaN and there are no seekable ranges before it.
- **The position write is the bare fire-and-forget lane, with no invalidation.** `StudyDesk` debounces it (1500 ms, hand-rolled like `NotebookEditorPane`'s) and sends `api.study.update(...).catch(() => {})` — no `useMutation`, no offline queue, and deliberately **no `invalidateQueries`**: it fires every few seconds of scrolling or playback, so invalidating would refetch the row being read. `fanficProgressCfg` can afford two invalidations per write only because it fires once per chapter. The desk flushes a pending write on unmount, which is the one moment the exact number matters. On the server side, **a position write does not bump `updated_at`** — where you are in a document is not an edit to it, and anything ordered by "recently changed" would otherwise be reordered by reading.

**Not built yet, on purpose:** the divider is fixed at 50/50 (there is no resizer anywhere in the app; the drag math would belong in `src/lib/` beside `paperImages.ts`), and the right half has no Paper-style handwriting page.
