# Writing (`src/components/Writing/`, `backend/routes/writing.py`, `backend/writing/`)

Two-panel layout: left nav (project list + a `WritingNav` with Chapters/Notes/Discussions/Canon sections) | full-width center panel that switches on the selected item: chapter → prose editor, note → note editor, discussion → chat view.

**DB tables**: `writing_projects`, `writing_chapters` (ordered by `position`), `writing_context_docs` (typed: `character | outline | worldbuilding | note`, plus `pinned`), `writing_context_doc_revisions`, `writing_canon_sources` + `writing_project_canon`. "Notes" in the UI/API are stored in `writing_context_docs` (HTTP paths are `/api/writing/.../notes`; the table name is legacy). Discussions reuse the existing `conversations` + `messages` tables; `conversations.writing_project_id` scopes them to a project, and the general Chat tab filters them out (`writing_project_id IS NULL`). Deleting a project deletes its discussions.

**Chapter/note editors**: plain `<textarea>` (not CodeMirror — prose, not code) with 1.5 s debounced auto-save; chapters add live word count and font-size shortcuts. The note editor has a **History** panel (`NoteHistory.tsx`).

## Discussions: a project works like an Ideas repo

The point of a discussion is to talk the book through and have what gets settled land in the project's notes, which are then the notebook the author writes from.

- **The server owns the discussion, not the browser.** `DiscussionView.tsx` sends only `{messages, conversationId}` to `/api/chat/stream`. `backend/writing/discuss.py`'s `run_config` sees `conversations.writing_project_id` and the route uses _its_ prompt, the `'writing'` toolset and _its_ project scope, ignoring any `systemPrompt`/`toolset`/`writingProjectId` in the body. So the reply runs on the durable path (`backend/delegate/runs.py` owns the row, a dropped connection loses nothing, the view polls with `shouldPollConversation`), the scope is a server fact rather than a claim from the client, and the iOS app takes part with no copy of the prompt. `backend/chat/autoreply.py` asks the same helper, so a **voice clip** dictated into a discussion is answered as Writing. It used to build the prompt client-side and persist the reply itself; that is why the old `'research'` + `writingProjectId` path still exists in `_toolbox` — kept for one release for stale clients.
- **Pinned notes replace the old checkbox panel.** Ticking a note still means "this matters on every turn", but it is `writing_context_docs.pinned` now, read into the prompt by `discuss.system_prompt` (budgeted at `MAX_PINNED_CHARS`; the rest are listed by title). The claim is about the note, so it belongs on the note — a checkbox set in React state was invisible to a second device. Pinning is **not** an edit: it does not move `updated_at`, so it cannot stale a pending update card.
- **The `'writing'` toolset**: the shared research chain (library first, web behind `delegate`), recall over the project (`writing_list`/`writing_read`/`writing_search`, `backend/writing/tools.py`), the two note proposals, and canon tools when the project has a ready canon source linked. No `remember`, no life wiki, no `add_todos` — those are about the user, not the book.
- **Notes land through confirm cards** (`backend/writing/proposals.py`): `propose_note` (new note; refused if the title exists) and `propose_note_update` (append by default — a local model rewriting a long note to add one fact loses three others; `replace` only when asked). They stage, never write. Accepting goes through `_accept_writing_note`/`_accept_writing_note_update` in `backend/routes/chat.py`, which take the **project from the message's conversation**, never from the editable card, and refuse an update whose note changed since the card was staged (`baseUpdatedAt`) — the card stays pending. The cards are `DelegateProposals`, the same component as the Chat tab.
- **Every change that can lose text leaves a revision** (`backend/writing/notes.py`, `writing_context_doc_revisions`, the `user_memory_revisions` pattern: `content` is the note _before_ the change). Sources are `'accept'` (an accepted proposal, with its message id), `'edit'` (the editor — coalesced to one per `EDIT_COALESCE_SECONDS`, or 1.5 s autosave would bury the revision that matters) and `'restore'` (restoring snapshots first, so a restore is undoable too).
- **Summarize** still distills the whole transcript into one new note via `backend/ai/writing.py` — useful at the end of a session, where proposals are for decisions made in the middle of one.
- Dictation on the desktop reuses `useRecorder` and **auto-sends** (a send-style surface, like the Chat tab).

## Canon: the source work a fanfic is set in

`backend/writing/canon_import.py` imports a **Fandom (MediaWiki) XML dump** — the `pages_current.xml.7z` a wiki's `Special:Statistics` page links to, a WikiTeam mirror's copy, or a plain `.xml`/`.gz`/`.bz2` — into one docpack-format SQLite file under `CANON_ROOT` (default `./data/canon/`). `CanonPanel.tsx` imports by upload or by URL (a wiki URL is resolved to its Statistics dump link), shows progress, and links sources to the project.

- **The file format is the Knowledge tab's docpacks; the registry is not.** `docpacks.search_file`/`read_file` are the same BM25 search and neighbour-window read, but a canon source is never a `knowledge_docpacks` row, because every installed docpack is searched by every chat — and a fandom wiki has no business in the Chat tab or an Ideas discussion. `CanonTools(project_id)` (`backend/writing/canon_tools.py`) sees only that project's linked, `ready` sources and fails closed like `WritingTools(None)`; the toolbox and the prompt line are only mounted when one exists.
- **Infoboxes are kept as `key: value` lines** (mwparserfromhell): that is where a fandom wiki keeps age, affiliation, first appearance, and a plain wikitext strip deletes them. **Redirects become alias rows** filed under the target page, so "Harry" finds and reads "Harry Potter". Only namespace 0 is kept. A `<!DOCTYPE` is refused (entity expansion); the dump is streamed with `iterparse` and cleared per page, so memory is flat however big the wiki is.
- **Canon vs notes**: the prompt says canon is what the original says and the author's notes are where this story diverges, so **notes win**. Every `canon_read` carries a CC BY-SA attribution line.
- Imports run on their own daemon thread (no model call — not the `llm_jobs` lane) with in-memory progress; `_reset_stale_canon_imports` marks an `importing` row `error` on restart. URL fetches go through `backend/research/web.assert_public_url` on every redirect hop, capped at `MAX_DOWNLOAD_BYTES`.
